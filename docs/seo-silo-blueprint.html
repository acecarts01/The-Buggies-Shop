Architectural blueprint and URL mapping audit

Golf Buggies Express · www.golfbuggiesexpress.com.au · prepared before any code, as your prompt requires. Everything below is measured from the live repository and site, not assumed. Nothing has been changed.

Read this first: where I recommend departing from the prompt, and why.
  1. Do not move the catalogue to /buggies/…. The site already has a working, validated silo (/shop/[category]/[slug], 10 categories, 102 product pages, 233 indexable URLs, all clean in Semrush and my crawler). Moving every URL means 233 redirects, a reset of Google's signals on pages that only just started indexing, and no ranking gain: "shop" versus "buggies" in a path is not a ranking factor. The prompt's goal (hierarchy, siloing, internal links) is met by extending what exists.
  2. Do not merge Brisbane and the Gold Coast into one URL. Both already exist as separate pages with different facts (distance, freight mode). One merged URL would delete a ranking page and make the survivor weaker for both searches.
  3. Do not create pages for products we do not sell. "Heavy-duty tipper cart" is not in the catalogue. A page for it would be a doorway page and a false claim.
  4. A "street legal" tag cannot list buggies as street legal. Registration depends on the state and the individual vehicle, and no product in the catalogue is documented as road-registrable. Calling products "street legal" would breach our no-fabricated-claims rule and Australian Consumer Law. I propose a factual "road access and lighting" collection instead (details in section 5).
  5. The URL words "golf carts" conflict with the brand rule ("buggies", not "carts") and with the owner-set primary keyword "buggies for sale". The site still ranks for "golf cart" queries through body copy, titles and the keyword map; the path should stay "buggies".
  6. I cannot promise "all Google Australia searches return to the site". Nobody can, and a plan built on that promise ends in doorway pages and a penalty. What is achievable is owning every search we genuinely satisfy, with no cannibalisation. That is what this plan does.

Gates a tag must pass to be generated (all checked at build)

  1. At least 4 products (the validator fails the build otherwise; below that, the products stay in their category and the tag does not exist).
  2. The tag must not equal a category or brand. "Walk-behind", "push", "Club Car" are already categories or brands, so they are excluded to stop two URLs competing for one search.
  3. One owner per keyword. Each tag declares its primary keyword; the build fails if two pages claim the same one or if a tag's keyword is already a category or product primary keyword (the existing keyword map is the registry).
  4. Unique 150-250 word intro written from real product facts (compatibility, battery chemistry, ranges from the spec data, Australian registration or terrain context). A similarity check against every sibling intro fails the build above a threshold, so intros cannot be templated clones.
  5. At least 3 FAQs, 40-65 words each (the site's existing standard), each answerable from the catalogue or an official source, never invented.
  6. Linked from at least 2 pages (the category and the product pages that carry it, plus the /tag/ index) so none is an orphan.
Road access and lighting (replaces "street legal"): a factual collection of lighting, mirror and indicator products, with the registration guide and the official state references. It states that conditional registration depends on the state and the vehicle and that we do not sell vehicles as road-registered. It never labels a product "street legal".

7. Internal link automation

Extend the engine we already have rather than build a second one. lib/autolink.ts already does what the prompt's linkify.tsx asks: server-side, whole-word, never inside an existing link, never self-linking, one link per destination per page, a per-paragraph cap, and a rule table generated from the keyword map. Limits kept exactly as the prompt asks: at most one automatic link per keyword per paragraph, plus a page-wide cap so a paragraph never reads as link spam. Link targets are verified at build: a rule that points at a URL that is not built fails the build, so a link can never 404.

8. FAQ accordions

  • Native <details>/<summary> (already shipped). It is keyboard operable with no JavaScript, and every answer is in the server-rendered HTML for crawlers, which Radix's collapsed panels are not guaranteed to be.
  • One FAQPage per page, generated from the same items that are visible (Google's rule: marked-up content must be on the page).
  • No standalone question URLs, as you specified.
  • Where it appears: product, category, brand, delivery and the new tag pages.

9. How I will prove "server-rendered, zero errors"

  1. Extend scripts/site-validate.mjs (already crawls raw HTML with JavaScript off): every internal link on every page must exist in the HTML, resolve with a 200 and no redirect; every tag, brand and region page must have a self-canonical, one H1, a unique title and description, BreadcrumbList, ItemList with canonical product URLs, FAQPage, and 150-250 words of intro.
  2. Cannibalisation check: no two indexable pages may share a primary keyword, and no tag's product set may be identical (or a subset within 90%) to a category's.
  3. Sibling-similarity check on intros and FAQ answers.
  4. Run the full set on a local production build, then on the live site after deploy, then Semrush and Search Console (sitemap resubmit, IndexNow) as before.
  5. Rollback: tags ship behind the sitemap gate, so a bad tag page can be dropped without touching any existing URL.
